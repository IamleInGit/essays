# 低功耗设计的四条主线

低功耗最常见的误解，是把它当成一个开关——调低主频、关几个外设，功耗就下来了。真做进去才发现它是一整条链：产品定义、器件选型、硬件设计、固件实现、测试验收，任何一环松掉，后面都白干。

做过几个项目之后，我把经验压成四条主线：**定目标、测基线、守原则、会调试**。

## 一、先定目标，再谈优化

"功耗要低"不是指标，可执行的指标是电流。

用续航反推：电池 300mAh，要求待机 180 天，出厂电量按 80% 算。

```
300mAh × 80% ÷ (180 天 × 24h) ≈ 56µA
```

这个 56µA 就是硬约束：它决定你能不能选那颗待机 3µA 的传感器、要不要加一级 LDO、晶振用有源还是无源。没有这个数字，后面所有讨论都会退化成"感觉还行"。

所以顺序是：产品定义 → 电池容量 → 器件选型 → 功耗基线 → 测试标准 → 软件实现。反过来做（先写完代码再想办法省电），代价通常是在最后砍功能。

## 二、测试能复现，才叫测试

同一块板、同一版固件，两个人测出两个数，说明测的不是功耗，是手法。

- **固定场景和操作**：环境温度、信号强度、音量、无线参数，都写进测试说明，不能只存在于测试员脑子里
- **大版本必测**：软件大版本发布、硬件改版，各测一次
- **留金机**：不同版本各留一台基准样机，出问题时至少还有对照
- **覆盖异常场景**：异常唤醒、反复重连、边界电压，这些地方的功耗常常比正常状态高一个数量级

小版本不必全测，但命中下面任何一类改动就要补测：

1. 驱动相关改动
2. 模块功能增减
3. 主频或时钟树变化
4. 模式切换逻辑（比如传感器的工作模式）
5. 输出功能变化
6. 关键任务执行频率上升，系统负载变大

## 三、三条原则，一堆具体动作

原则只有三句：**留余量**、**不依赖自动**、**把异常当正常**。

落到代码上，大多是这几件事：

- **显式配置每一个引脚**，包括封装里没引出来的。浮空的输入脚会一直抖，抖一下漏一点电
- **分级进入低功耗**：不是一步睡到底，而是逐级关外设、关时钟，每一级都能单独验证
- **关外设必须同时关时钟**。只关外设不关时钟，那点电流还在
- **看门狗要喂得上**：低功耗下 SysTick 停了，喂狗得靠 RTC 或低功耗定时器
- **时钟切换自己做**，唤醒后留够晶振起振时间，别让程序在时钟没稳的时候跑飞

## 四、调试：先保现场，再动手

低功耗的问题三分靠写、七分靠调，最怕一上来就改代码。

**保护现场**是第一原则。低概率问题先留证据：dump 一份 flash、记下软硬件版本、确认问题概率（单例还是必现）。然后再按层级逐步破坏——先换环境，再软复位，最后才动硬件。破坏一步，记一步。

具体手法按场景选：

| 手法 | 什么时候用 |
| :--- | :--- |
| 场景关联 | 能稳定复现，知道从哪个功能触发，直接查对应模块 |
| 版本回退 | 必现的软件问题，一路回退到原厂 SDK，确认是不是自己引入的 |
| 交叉验证 | 单例的硬件问题，交换模块，看异常跟着谁走 |
| 解耦排除 | 知道有问题但不知道在哪，逐个屏蔽模块 |
| 波形分析 | 有功耗曲线，对比正常和异常的阶段差异 |

## 最后

低功耗的本质不是某项技术，而是**对每一个状态的掌控**：知道它现在在哪个模式、哪些外设还开着、下一次唤醒由谁触发。掌控不了的状态，迟早会在某一版固件里变成几毫安的漏电。
